## [Unreleased]

### Added
- **MCP `notifications/progress` emitted while polling container status during publishing** — the Meta Graph publishing flow polls a container for up to 5 minutes (`VIDEO_PROCESSING_TIMEOUT = 300` in `src/utils/container.ts`) before calling `/media_publish`, but the publish handlers in `src/tools/instagram/publishing.ts` and `src/tools/threads/publishing.ts` previously ignored the SDK-provided `extra` callback parameter, so MCP hosts saw the tool call freeze for half a minute on a Reel and up to five on a video Story. `pollContainerStatus()` now accepts an `onProgress?: (progress, total, message?) => void` hook that fires after every successful poll (1-based so the first emission is already `>0` and the MCP "strictly increasing per token" rule holds); the helper itself stays MCP-agnostic and has no `@modelcontextprotocol` import. A new `makeProgressNotifier(extra, mode)` factory in `src/utils/progress.ts` returns `undefined` when no `progressToken` is attached to the request — so publish handlers pass the result straight through `{ onProgress: makeProgressNotifier(extra) }` without null checks — and otherwise returns a closure that builds the `notifications/progress` event and fire-and-forget calls `extra.sendNotification()` with a `.catch(() => {})` so a closed transport (client disconnect, request cancel) never converts a successful upload into a failed MCP response. Single-poll publishers (`ig_publish_photo`, `ig_publish_video`, `ig_publish_reel`, `ig_publish_story`, `threads_publish_image`, `threads_publish_video`) use `mode: "single"` and forward the raw `(attempt, maxAttempts)` pair so a client can render a determinate progress bar with `total = maxAttempts`. Carousels (`ig_publish_carousel`, `threads_publish_carousel`) use `mode: "shared"` instead: child container polls run in parallel via `Promise.all` and the per-call attempt counters would otherwise emit non-monotonic `progress` values across the single tool-call `progressToken`, so the shared closure replaces them with an internal counter (`++counter`) and omits `total` (cannot be known ahead of time across N parallel children) — the same shared notifier is passed to every child poll and to the final carousel container poll, keeping `progress` strictly monotonic across the whole tool invocation. `threads_publish_text` is intentionally skipped: it defaults to `auto_publish_text=true` (single `/threads` call, no polling) and only takes the legacy two-step path when the caller passes `auto_publish: false`. The notifier also exposes a `.stop()` method that flips an `alive` flag inside the closure — both carousel handlers call it from a `finally` block so that a `Promise.all` rejection (one child container goes ERROR) cannot leave the surviving sibling polls emitting `notifications/progress` after the tool call has already returned, which would violate MCP's "no progress after request completion" lifecycle rule. Verified against the SDK's `ProgressNotificationParamsSchema` in `@modelcontextprotocol/sdk/dist/esm/types.d.ts` — `{ progressToken, progress, total?, message? }` with `method: "notifications/progress"` ([#64](https://github.com/exileum/meta-mcp/issues/64))
- **MCP server `instructions` string sent during `initialize`** — the `McpServer` constructor's optional `instructions: string` (typed in `@modelcontextprotocol/sdk/dist/esm/server/index.d.ts` `ServerOptions`) was previously unset, so LLM clients had no description of what the server can do, what env vars it needs, or what shape its responses take, and had to either re-read the README or infer everything from individual tool descriptions. A new `SERVER_INSTRUCTIONS` constant at the top of `src/index.ts` (single-source) is now passed to **both** `McpServer` constructors — the live stdio server in `main()` and `createSandboxServer()` consumed by the Smithery sandbox runtime — so the same string ships to every MCP host. It covers: (a) what the server does (Instagram + Threads management via the Meta Graph API), (b) required env vars per platform (`INSTAGRAM_ACCESS_TOKEN` + `INSTAGRAM_USER_ID` for IG, `THREADS_ACCESS_TOKEN` + `THREADS_USER_ID` for Threads, plus `META_APP_ID` + `META_APP_SECRET` for the token-rotation tools), (c) the two-step publish flow that's hidden behind a single MCP call and the 30 s image / 5 min video processing windows, (d) that publish calls emit `notifications/progress` when the client sets a `progressToken` (cross-references the #64 fix in the same PR), and (e) the `_rateLimit` envelope on every tool response so callers can throttle subsequent calls without parsing headers themselves. Kept terse — the SDK serializes the string inline in every initialize handshake. No public API change for npm consumers ([#63](https://github.com/exileum/meta-mcp/issues/63))
- **Graceful shutdown on `SIGINT` / `SIGTERM`** — `main()` in `src/index.ts` now wires the live `McpServer` into a new `setupShutdownHandlers()` helper (`src/shutdown.ts`) that listens for both signals, awaits `server.close()`, and then calls `process.exit(0)`. Previously the entry point registered no signal handlers, so Node's default action terminated the process immediately — `StdioServerTransport.close()` never ran, its `_readBuffer` was never cleared, the stdin `data`/`error` listeners stayed attached, and any frame still in the stdout buffer could be dropped, leaving MCP hosts with an abrupt EOF instead of a clean disconnect. The bigger observable win is Docker: the project's `Dockerfile` runs `ENTRYPOINT ["node", "dist/index.js"]` with no init shim (no `tini`/`dumb-init`), so `node` is PID 1 and the Linux kernel does **not** deliver default signal actions to PID 1 — without an explicit handler, `docker stop` waited the full 10 s grace period before `SIGKILL`ing the container; with the handler, the container shuts down within milliseconds of receiving `SIGTERM`. The helper hardens four real edge cases beyond the bare snippet recommended in the issue: (a) `server.close()` is wrapped in `try`/`catch` and a rejection routes to `exit(1)` instead of becoming a swallowed `unhandledRejection` from the `async` listener; (b) a `shuttingDown` flag turns a second signal (Ctrl+C spam, `docker stop` after a hung shutdown, etc.) into a no-op that logs `[meta-mcp] <signal> received during shutdown — ignoring` rather than racing a second `close()` call (`StdioServerTransport.close()` is itself idempotent, but the flag keeps the log output unambiguous); (c) the `process.on(signal, …)` listener is a plain function that calls `void shutdown(signal)`, so the registered listener is never an `async` function and Node never sees a dangling promise; (d) `server.close()` races against a `SHUTDOWN_TIMEOUT_MS = 5_000` deadline via `Promise.race` (with `clearTimeout` in a `finally` so the timer never leaks past a fast close), so a hung transport drain still exits the process well under Docker's 10 s grace period — without the deadline the Docker win would be conditional on `close()` always being fast. Both stderr log lines (`[meta-mcp] <signal> received — shutting down gracefully` and the error path) go through `console.error` — same stderr-safe pattern already used by `loadConfig()`'s `warnIfMisconfigured()` warnings, so they don't corrupt the JSON-RPC frames on stdout. `createSandboxServer()` is deliberately unchanged: it's consumed by the Smithery sandbox runtime which owns the process lifecycle, and registering process-wide signal handlers from a sandbox factory would leak into the host. The helper accepts optional `exit` / `log` hooks for testability (defaults to `process.exit` / `console.error`); the new `src/shutdown.test.ts` uses them plus a `vi.spyOn(process, "on")` capture to verify both signals call `close()`, a rejected `close()` still exits non-zero, and a second signal during shutdown is a no-op — without ever dispatching a real signal that would terminate vitest ([#78](https://github.com/exileum/meta-mcp/issues/78))
- **Network errors from `fetch()` are now normalized into a typed `MetaNetworkError`** — `MetaClient.request()` previously rethrew raw `TypeError("fetch failed")` / `DOMException(name="TimeoutError")` after retries were exhausted, surfacing as unhelpful tool messages like `"Publish photo failed: The operation was aborted"` with no signal that this was a 30-second timeout vs. a bug vs. a DNS failure. Failures now arrive as `MetaNetworkError` (new export from `src/utils/errors.ts`) with explicit endpoint context: `Meta API POST /{ig-user-id}/media: request timed out after 30s` for timeouts, `Meta API GET /me: network error — fetch failed` for DNS / `ECONNREFUSED` / TLS errors. The original error is preserved on `err.cause` (ES2022, supported in Node 22+ per the `engines.node` requirement) so callers debugging in Node still have the full chain. `formatErrorResponse()` continues to classify the wrapped error as `error_type: "network"` with the same remediation hint — `categorize()` now detects `MetaNetworkError` explicitly so the `name === "AbortError"|"TimeoutError"` checks (which would otherwise miss the renamed class) keep working. No public API change for MCP clients: the JSON error envelope shape from [#114](https://github.com/exileum/meta-mcp/issues/114) is unchanged; only the `message` and `raw` fields gain endpoint context. `kind` is exposed as `"timeout" | "network"` on `MetaNetworkError` for callers (or future code) that wants to branch without parsing the message; `AbortError` is folded into `"timeout"` defensively in case any runtime still uses the older name even though [WHATWG `AbortSignal.timeout`](https://dom.spec.whatwg.org/#dom-abortsignal-timeout) mandates `"TimeoutError"` ([#72](https://github.com/exileum/meta-mcp/issues/72))
- **`MetaClient.updateConfig(partial: Partial<MetaConfig>): void`** — public method to merge a partial `MetaConfig` into the running client's in-memory config without recreating the instance. The implementation is intentionally minimal (`this.config = { ...this.config, ...partial }`) so any future runtime mutation (additional credentials, user-ID rotation if Meta ever requires it) lands here rather than spreading per-field setters. The private `config` field stays private — only the new method exposes mutation, and consumers still cannot read the credentials back. `ig()` / `threads()` / `meta()` already re-read `this.config.<field>` on every call, so no URL cache or per-platform base needs invalidation when the partial lands ([#65](https://github.com/exileum/meta-mcp/issues/65))

### Changed
- **`meta-mcp://threads/profile` resource now also returns `is_eligible_for_geo_gating`** — the namespaced Threads profile resource silently lagged behind `threads_get_profile` since [#97](https://github.com/exileum/meta-mcp/issues/97) added the geo-gating eligibility flag to the tool's default fields but left the parallel resource handler in `src/resources/threads.ts` untouched. The tool/resource pair are now backed by a single shared `THREADS_PROFILE_FIELDS` constant, so resource consumers can self-check geo-gating eligibility (the same use case the tool change enabled in [#97](https://github.com/exileum/meta-mcp/issues/97)) without making a second `threads_get_profile` call. The drift was the motivating example for [#89](https://github.com/exileum/meta-mcp/issues/89) and is exactly the kind of inconsistency the dedup is meant to make impossible going forward. Additive only — every existing field in the JSON payload remains; the response now carries one extra boolean ([#89](https://github.com/exileum/meta-mcp/issues/89), [#97](https://github.com/exileum/meta-mcp/issues/97))
- **Default Meta API field strings centralized in a new `src/constants/fields.ts` module** — the same field lists were previously hardcoded across tools and resources: Instagram profile fields lived in both `src/tools/instagram/profile.ts` and `src/resources/instagram.ts`; Threads profile fields lived in both `src/tools/threads/profile.ts` and `src/resources/threads.ts` (and had already drifted, see above); the Instagram media field list lived in `src/tools/instagram/media.ts` twice (the `ig_get_media` schema default and the inline `ig_get_media_list` request) and as a `thumbnail_url`-less variant in `src/tools/instagram/hashtags.ts` (used by both `ig_get_hashtag_recent` and `ig_get_hashtag_top`); and `THREADS_MEDIA_FIELDS` was a local `const` in `src/tools/threads/media.ts` that no future resource handler could reuse. The new module exports `IG_PROFILE_FIELDS`, `IG_MEDIA_FIELDS`, `IG_HASHTAG_MEDIA_FIELDS`, `THREADS_PROFILE_FIELDS`, and `THREADS_MEDIA_FIELDS`; all seven affected files import from there. Single-tool field constants (`BUSINESS_DISCOVERY_DEFAULT_FIELDS`, `GET_CONVERSATIONS_DEFAULT_FIELDS`, `MENTIONED_COMMENT_DEFAULT_FIELDS`, `TAGGED_MEDIA_DEFAULT_FIELDS`, `REPLIES_*_FIELDS`, `GET_COMMENTS_DEFAULT_FIELDS`, etc.) stay local to their handler module since they have no cross-file duplication — out of issue scope. No public API change for MCP clients; the existing `gif_url` / `gif_attachment` regression tests from [#139](https://github.com/exileum/meta-mcp/issues/139) / [#146](https://github.com/exileum/meta-mcp/issues/146) and the exact-string assertion on `ig_get_media` default fields continue to pass against the shared constants ([#89](https://github.com/exileum/meta-mcp/issues/89))
- **Tool names referenced by `content_publish` and `analytics_report` prompts now flow through a `PROMPT_TOOL_NAMES` constant cross-checked against the live tool registry** — the two prompts previously hardcoded 9 tool names as raw strings in their instruction text (`ig_publish_photo`, `threads_get_user_insights`, etc.); a rename, removal, or split (e.g., a future `ig_publish_video` deprecation cleanup, or the [#37](https://github.com/exileum/meta-mcp/issues/37)-style migrations that already touched every other registration site) would silently leave the prompt pointing at a non-existent tool — the AI would call it, get `Tool not found`, and waste tokens recovering. The new `PROMPT_TOOL_NAMES` const exported from `src/prompts/index.ts` enumerates every tool name the prompts reference, and a new `src/prompts/index.test.ts` test runs `registerAll()` with a mock and asserts every value in the const matches a registered tool. A future rename now surfaces as a CI failure on the same PR that drops the tool, not after-the-fact in an MCP client. `ig_publish_video` was deliberately dropped from the prompt — the deprecation tip from [#118](https://github.com/exileum/meta-mcp/issues/118) is already in the tool description itself, so steering callers to `ig_publish_reel` for video content (the only tool in `PROMPT_TOOL_NAMES` for `content_type=video` on Instagram) is the simpler signal. `threads_publish_carousel` was added — the previous static prompt didn't mention it even though it ships in the SDK, so `content_type=carousel` previously fell through to the generic Threads list ([#88](https://github.com/exileum/meta-mcp/issues/88))
- **`pollContainerStatus()` switched from a fixed 5-second polling cadence to exponential backoff with jitter** — `src/utils/container.ts` previously slept `interval` ms (default 5_000) between every status check, producing up to 60 GETs over the 300 s `VIDEO_PROCESSING_TIMEOUT` budget for a slow-transcoding video, and (after the [#48](https://github.com/exileum/meta-mcp/issues/48) parallel-carousel change) firing every child's poll on the same tick — a thundering herd that all hit `graph.{instagram,threads}.{net,com}/{container-id}?fields=status[_code]` simultaneously. The loop now grows each successive wait by `POLL_BACKOFF_FACTOR = 1.5`, capped at `MAX_POLL_INTERVAL_MS = 30_000`, and adds `random() * POLL_JITTER_MS` (500 ms) of jitter per attempt so concurrent carousel children stagger their polls naturally. The previous attempt-count loop (`maxAttempts = ceil(maxWait * 1000 / interval)`) was replaced with a time-budget loop (`deadline = Date.now() + maxWait * 1000`), so the timeout still triggers at the documented `maxWait` boundary even though individual delays are non-uniform. Concrete impact: a 300 s video budget drops from ~60 polls to ~11 (5, 7.5, 11.25, 16.875, 25.3, 30, 30, 30, 30, 30 s elapsed); a 30 s image budget drops from ~6 to ~2. The timeout error string is unchanged (`<label> processing timed out after <maxWait>s (last status: <lastStatus>)`) so existing message-matching tests stay green. New options on `PollContainerOptions` (`maxInterval`, `backoffFactor`, `jitterMs`, `random`) let tests pin determinism — defaults are baked in so `waitForIgContainer()` / `waitForThreadsContainer()` keep their two-argument signatures and no caller code needed updating. The existing `interval` option is preserved as the **base** delay; passing `interval: 500` keeps the first poll quick even with backoff enabled. Aligns with Meta's [content-publishing guidance](https://developers.facebook.com/docs/instagram-platform/content-publishing/) ("query a container's status once per minute, for no more than 5 minutes") while staying tighter than 60 s so image containers — which typically finish on the first poll — don't pay a needless backoff penalty ([#98](https://github.com/exileum/meta-mcp/issues/98))
- **Publish-tool error messages now include the failing step and container ID** — `src/utils/errors.ts` `formatErrorResponse(error, label, context?)` gained an optional `context?: { step?: string; containerId?: string }` parameter that augments the human-readable `message` and surfaces the same data as structured `step` / `container_id` fields on the JSON error payload. Every publishing handler in `src/tools/{instagram,threads}/publishing.ts` and `src/tools/threads/replies.ts` now tracks the current phase (`container creation` → `processing` → `publishing`) and the assigned container ID through outer-scope variables, passing them on the catch path. Carousel handlers track a richer step set (`child container creation` / `child processing` / `parent container creation` / `parent processing` / `publishing`) and, since carousel children run under `Promise.all` in parallel, capture the **first-failing** child's step and ID via shared `firstFailingChildStep` / `firstFailingChildId` variables — JavaScript's single-threaded execution guarantees the first-rejecting child's catch wins the `=== undefined` race that gates the assignment. Before: `"Publish photo failed: Meta API POST /17841405822304914/media_publish (400): bad container"` — operators couldn't tell whether the container existed (and would expire), whether processing timed out (retryable), or whether the final publish failed (container possibly reusable). After: `"Publish photo failed at publishing (container: 17889615324): Meta API POST /17841405822304914/media_publish (400): bad container"` plus `payload.step === "publishing"` and `payload.container_id === "17889615324"` for programmatic branching. Back-compat: `formatErrorResponse(error, label)` calls without `context` produce the existing message verbatim and add no new payload fields; only the 9 publish handlers populate them. The structured fields are documented in the JSON envelope in `README.md` "Troubleshooting" and in `llms.txt` `## Error Responses` so AI agents can self-debug. `step` is intentionally a plain string rather than a discriminated union — the carousel handlers need 5 values that don't fit a single tuple cleanly, and clients only need to match prefixes (`container creation`, `child container creation`, etc.) ([#99](https://github.com/exileum/meta-mcp/issues/99))
- **Migrated the remaining resource and prompt registrations off the deprecated `server.resource()` / `server.prompt()` overloads** — `@modelcontextprotocol/sdk@1.29.0` marks the positional-argument forms of both methods as `@deprecated` in favor of the config-object `server.registerResource()` / `server.registerPrompt()` form. The 57 tool registrations were already migrated in [#37](https://github.com/exileum/meta-mcp/issues/37) (`CHANGELOG.md` v7.0.0 — "Migrated all tool registrations from the deprecated `server.tool()` overload to `server.registerTool()`"), so this PR finishes the remaining 4 sites: `instagram-profile` and `threads-profile` in `src/resources/{instagram,threads}.ts`, plus `content_publish` and `analytics_report` in `src/prompts/index.ts`. Resources are a pure method rename — the `(name, uri, metadata, callback)` argument shape is identical between `resource()` and `registerResource()`. Prompts move the description into the config object: `server.prompt(name, description, {}, cb)` → `server.registerPrompt(name, { description }, cb)`. The handler bodies, resource URIs, prompt messages, and MCP-client-visible behavior are byte-identical to before — only the SDK registration wrapper differs. Test mocks in `src/resources/instagram.test.ts`, `src/resources/threads.test.ts`, and `src/register-all.test.ts` were updated to spy on `registerResource`/`registerPrompt` instead of `resource`/`prompt`; the captured-array assertions in `src/register-all.test.ts` and the per-resource handler tests are unchanged. Closes [#79](https://github.com/exileum/meta-mcp/issues/79)
- **`MetaClient` HTTP method parameter narrowed from `string` to `HttpMethod = "GET" | "POST" | "DELETE"`** — `request()`, `ig()`, `threads()`, and `meta()` previously accepted any string for the HTTP method, so a typo like `client.ig("DELET", ...)` would compile and then fall through the `isWrite = method !== "GET" && method !== "DELETE"` check in `request()`, sending the call as `POST` instead of the intended `DELETE` — a silent create/modify in place of a delete. The new `HttpMethod` union (exported from `src/services/meta-client.ts`) rejects unknown methods at compile time; the same narrowing is propagated to `MetaApiError.method` and the `ApiCallFn` type used by `pollContainerStatus()` in `src/utils/container.ts` so the type stays consistent end-to-end. No runtime behavior change — every existing call site already used one of the three literals. Internal-only refactor: `MetaClient` is not re-exported from `src/index.ts`, so npm consumers of `@exileum/meta-mcp` are unaffected ([#74](https://github.com/exileum/meta-mcp/issues/74))
- **`meta_exchange_token` and `meta_refresh_token` now auto-apply the new token to the running MetaClient — runtime token rotation no longer requires a server restart** — `MetaConfig` was created once at startup from environment variables and stashed on a private `MetaClient.config` field; both token-rotation tools hit Meta's `/access_token` and `/refresh_access_token` endpoints and returned the new long-lived token in their MCP response, but never wrote it back into the running client, so subsequent IG/Threads tool calls kept using the original (often soon-to-expire) token until the operator restarted the server with refreshed env vars. Both handlers in `src/tools/meta/auth.ts` now call a new `client.updateConfig(partial)` immediately after a successful exchange/refresh, merging `instagramAccessToken` or `threadsAccessToken` into the in-memory config (the platform parameter picks the field). The next `client.ig()` / `client.threads()` request picks up the rotated token without restart. The MCP response is unchanged — `access_token`, `token_type`, `expires_in` are still returned verbatim, so callers can persist the new value to env vars / secret stores for the next process restart. A single `[meta-mcp] <Platform> access token updated in-memory after <tool>; subsequent tool calls will use the new token (no restart required).` line is logged to stderr per successful auto-apply (safe for stdio MCP, no token value in the log). The auto-apply is a no-op when the response has no `access_token` (defensive guard against malformed Meta responses) and on the error path the existing `catch`/`formatErrorResponse` runs instead, leaving the stored token untouched. Verified against the [Instagram long-lived token docs](https://developers.facebook.com/docs/instagram-platform/instagram-api-with-instagram-login/business-login) and [Threads long-lived token docs](https://developers.facebook.com/docs/threads/get-started/long-lived-tokens) — both endpoints return `{ access_token, token_type, expires_in }` with no `user_id`, so the configured `INSTAGRAM_USER_ID` / `THREADS_USER_ID` stay unchanged ([#65](https://github.com/exileum/meta-mcp/issues/65))
- **Replaced ~105 manual `if (param) params.key = param` guard clauses across 12 tool files with a shared `buildParams()` helper** — added `src/utils/params.ts` exporting `buildParams(required, optional)`, a typed merge helper that skips only `undefined` values and preserves `null`/`0`/`false`/`""`. The previous truthy-check pattern had already produced one confirmed bug (`thumb_offset=0` silently dropped, see [#32](https://github.com/exileum/meta-mcp/issues/32), patched individually with `!== undefined`) and kept the same hazard latent for any future numeric/boolean parameter. The mix of `if (x)` and `if (x !== undefined)` across the handlers also drifted apart over time, so the helper now enforces a single rule by construction. Affected handlers span every Instagram and Threads tool module: publishing (`ig_publish_photo`, `_video`, `_carousel`, `_reel`, `_story`, `threads_publish_text`, `_image`, `_video`, `_carousel`, `threads_search_locations`), media/comments/mentions list endpoints (`ig_get_media_list`, `ig_get_comments`, `ig_get_replies`, `ig_get_tagged_media`, `ig_get_hashtag_recent`, `ig_get_hashtag_top`, `ig_get_collaboration_invites`, `threads_get_posts`, `threads_search_posts`, `threads_get_mentions`, `threads_get_replies`), DM listings (`ig_get_conversations`, `ig_get_messages`), insights (`ig_get_account_insights`, `threads_get_user_insights`), and `threads_reply`. The helper's `optional` argument is typed as `Record<string, FormParamValue | undefined>`, mirroring the runtime guard in `appendFormParams()` from [#81](https://github.com/exileum/meta-mcp/issues/81) so accidental object/array values are rejected at compile time. Non-trivial cases that don't fit the helper stay imperative: the derived `poll_attachment` / `gif_attachment` / `text_attachment` JSON payloads in `threads_publish_text` are pre-computed into local variables and then passed in; the existing mutating helpers `applyShareToIgStory()` and `applyAllowlistedCountryCodes()` are still called after `buildParams()` since they handle non-1:1 key mappings and computed string joins. **Behavior note**: an explicit empty string (`""`) on an optional input now passes through to the Meta API (previously silently skipped by the truthy check); Meta rejects empty values on every affected field, so practical impact is none. Matches the same trade-off documented in [#148](https://github.com/exileum/meta-mcp/issues/148) (`fields`/`metric` defaults). No public API change — input schemas, tool names, response shapes, and JSON-encoded payload contents are byte-identical for every existing caller; verified by the full 643-test vitest suite continuing to pass without modification ([#82](https://github.com/exileum/meta-mcp/issues/82))
- **Stricter TypeScript compiler flags enabled in `tsconfig.json`** — added `noUnusedLocals`, `noUnusedParameters`, `noUncheckedIndexedAccess`, and `noFallthroughCasesInSwitch` on top of the pre-existing `strict: true`. The first two surface dead code that survives a refactor (unused variables and unused function parameters); `noUncheckedIndexedAccess` is the high-value one — it widens every array/object index access to `T | undefined` so a typo like `items[0].id` on a possibly-empty array is caught at compile time instead of crashing as a runtime `TypeError` on the user's first empty result page; `noFallthroughCasesInSwitch` is a no-op against the current `src/` tree (no `switch` statements yet) but lands as a forward-looking guard so a new `switch` block cannot silently fall through. The only existing source-code site surfaced by the new flags was the `text_attachment_styling` overlap-detection loop in `src/tools/threads/publishing.ts` — the bounded `for (let i = 1; i < sorted.length; i++)` iteration already guarantees `sorted[i]` and `sorted[i-1]` are defined, so the loop body now binds `const prev = sorted[i - 1]!` and `const curr = sorted[i]!` to communicate that invariant to the type checker without changing the comparison or the validation message; emitted JavaScript is byte-equivalent to before since TypeScript-only `!` assertions erase at compile time. `skipLibCheck: true` is intentionally kept on for build speed — the issue's note about periodically running `tsc --noEmit --skipLibCheck false` to surface hidden `node_modules` type incompatibilities is a manual-audit suggestion, not a default-on recommendation, so it stays a maintainer-discretion task ([#95](https://github.com/exileum/meta-mcp/issues/95))
- **`src/index.ts` no longer triggers a full server bootstrap as a module-import side effect** — every setup statement that previously ran at module top-level (`loadConfig()`, `new MetaClient(config)`, `new McpServer(...)`, `registerAll(server, client)`, plus the unconditional `main().catch(...)` invocation at the bottom of the file) is now encapsulated inside `main()`, and `main()` runs only when this module is the CLI entry point. The previous shape made `import { createSandboxServer } from "@exileum/meta-mcp"` (or any unit test that touched `src/index.ts`) trigger the full server bootstrap on import: `loadConfig()` read `process.env` (and `process.exit(1)`'d the entire process on a malformed config), `MetaClient` was instantiated against those env vars, all 58 tools / 2 resources / 2 prompts were registered against the production `McpServer`, and finally `StdioServerTransport` was attached to `process.stdin` / `process.stdout` — every one of those a hazard for testing and for any library consumer of the sandbox factory. The new shape uses a small `isInvokedAsCli()` guard that compares `import.meta.url` against `pathToFileURL(realpathSync(process.argv[1])).href` so the CLI paths (`node dist/index.js`, the npm `bin` shim via `npx @exileum/meta-mcp`, and `tsx src/index.ts` for `npm run dev`) still boot normally, while `await import("./index.js")` from a test or downstream import does nothing. The literal recommendation in the issue ("move setup inside `main()`") is necessary but not sufficient on its own — without the CLI guard, `main()` still runs unconditionally at module load and the testability problem remains; the guard is what actually delivers the fix. `createSandboxServer()` is byte-identical to before — same name, same `McpServer` return type, same registered surface (the snapshot in `src/register-all.test.ts` already locks the surface in by tool name and registration order). `package.json` `bin` / `main` / `exports` and the `Dockerfile` `ENTRYPOINT ["node", "dist/index.js"]` are unchanged, so npm consumers and container images see no path change. The new `src/index.test.ts` is the regression guard: one test snapshots `process.listenerCount("SIGINT" / "SIGTERM")` across `await import("./index.js")` and asserts the counts are unchanged (proving `setupShutdownHandlers` — and therefore `main()` — never ran on import); the other sets `META_APP_ID="definitely-not-numeric"` (which would fail `MetaConfigSchema`'s `^\d*$` regex if `loadConfig()` ever ran) and asserts `createSandboxServer()` still returns an `McpServer` — an accidental call to `loadConfig()` from either the import or the sandbox factory would `process.exit(1)` and tear down the vitest worker as a loud failure. The issue's third bullet ("Cannot conditionally initialize: No way to skip Instagram registration if only Threads is configured") is intentionally out of scope — it would require touching `registerAll`'s signature and tool-grouping ([#91](https://github.com/exileum/meta-mcp/issues/91))

### Fixed
- **Instagram text fields now enforce Meta API length limits at the schema boundary** — every user-provided text input on the Instagram tools previously declared a bare `z.string()`, so overlong captions/comments/DMs/alt-text strings passed Zod validation and only failed at the Meta API with a generic `(#100) The message is too long` error. The same gap existed even on tools whose `.describe()` already advertised the limit (`ig_publish_photo`'s `caption` description said "max 2200 chars" but the schema didn't enforce it). Closes the asymmetry with the Threads publishing tools, where `z.string().max(500)` has been enforced on `threads_publish_text` and `threads_reply` since the original implementation. Character-based limits are counted in **Unicode code points**, not JavaScript's default `.length` (UTF-16 code units), via `[...s].length` inside a `.refine()` — `z.string().max(N)` would have rejected a 1500-emoji caption (1500 code points, 3000 UTF-16 units) even though Meta's "Maximum 2200 characters" budget is comfortably above it. Affected fields: `ig_post_comment.message` and `ig_reply_to_comment.message` (now `.min(1)` + code-point refine `≤2200`); `ig_publish_photo.caption`, `ig_publish_video.caption`, `ig_publish_carousel.caption`, and `ig_publish_reel.caption` (now code-point refine `≤2200`, `.optional()`); `ig_publish_photo.alt_text` and `ig_publish_carousel.items[type=IMAGE].alt_text` (now code-point refine `≤1000`, `.optional()`); and `ig_send_message.message`, which uses a byte-aware `.refine((s) => new TextEncoder().encode(s).length <= 1000)` because Meta's [Instagram Messaging API docs](https://developers.facebook.com/docs/instagram-platform/instagram-api-with-instagram-login/messaging-api) document the cap as "1000 bytes" of UTF-8, not 1000 characters — a 251-emoji string is 1004 bytes but only 251 code points and would otherwise sail past a naive `.max(1000)` straight into Meta's rejection. The shared `captionSchema` and `altTextSchema` constants in `src/tools/instagram/publishing.ts` keep all four caption sites and both alt_text sites on a single source of truth. Limits verified against the [Instagram media reference](https://developers.facebook.com/docs/instagram-platform/instagram-graph-api/reference/ig-user/media/) (caption: "Maximum 2200 characters, 30 hashtags, and 20 @ tags"; alt_text: "Alternative text, up to 1000 character, for an image"). `ig_publish_story` has no caption or alt_text parameter so it's untouched; `ig_publish_carousel.items[type=VIDEO]` carries no `alt_text` field per the existing discriminated-union shape so the byte-budget for VIDEO children is unaffected. The `TextEncoder` byte-count approach mirrors the conversion already used in `threads/publishing.ts` for `text_attachment_styling` char→byte offset translation. For valid callers nothing changes; over-limit callers now see a clear Zod error before the HTTP round-trip ([#108](https://github.com/exileum/meta-mcp/issues/108))

## [7.0.0] — 2026-05-22

### Added
- **`MetaClient` now self-throttles on `x-app-usage` to stay under Meta's per-app quota** — `parseRateLimit()` had been surfacing the snake_case header (`call_count`, `total_cpu_time`, `total_time`) as the camelCase `_rateLimit` field on every tool response since [#20](https://github.com/exileum/meta-mcp/issues/20), but the client never consulted the data and a burst of MCP tool calls walked straight into Meta's 100%-threshold throttle (HTTP 429, up to one hour lockout per the [Meta rate-limiting docs](https://developers.facebook.com/docs/graph-api/overview/rate-limiting/)). The client now caches the most recent `x-app-usage` snapshot on the `MetaClient` instance and sleeps before the next `fetch()` once `max(callCount, totalCpuTime, totalTime)` crosses one of two thresholds: 80% → 1000 ms slowdown, 90% → 5000 ms backoff. The `max(...)` picks up whichever quota Meta is rate-limiting on at the moment (request count, wall-clock, or CPU — Meta throttles on whichever hits 100% first). The first request after startup is never throttled (no snapshot yet). Snapshots only update when the header is present, so OAuth token endpoints (`graph.instagram.com/access_token`, `graph.threads.net/refresh_access_token`, etc.) leave existing throttle state intact rather than clearing it; the snapshot is also refreshed on error responses so a 429 immediately tightens the next call. Snapshots older than `RATE_LIMIT_SNAPSHOT_TTL_MS` (1 hour, Meta's rolling window) are discarded so a long-idle client doesn't pay a spurious backoff on its first post-idle call. The 30 s abort timer (`AbortSignal.timeout(30_000)`) is now armed **after** the throttle sleep so a 5 s backoff at high `x-app-usage` no longer eats into the network budget. As a side effect, `pollContainerStatus()` (used by every IG/Threads publish that creates a media container) now self-throttles too — a video publish near 90% usage may exhaust its 300 s timeout faster, which is the correct behavior: we *want* polling to slow down when we're near the cap. `parseRateLimit()` also gained defensive numeric coercion (`Number(v)`) so a future Meta API tweak (numbers shipped as strings) keeps producing usable values instead of silently leaving fields `undefined`. Each throttled call logs a single `[meta-mcp] x-app-usage at N%…` line to stderr (safe for stdio MCP). Thresholds and delays are exported as named constants (`RATE_LIMIT_SLOWDOWN_THRESHOLD`, `RATE_LIMIT_BACKOFF_THRESHOLD`, `RATE_LIMIT_SLOWDOWN_MS`, `RATE_LIMIT_BACKOFF_MS`, `RATE_LIMIT_SNAPSHOT_TTL_MS`) so the regression tests reference them by name. Issue [#61](https://github.com/exileum/meta-mcp/issues/61) (retry/backoff on 429) and [#72](https://github.com/exileum/meta-mcp/issues/72) (network error normalization) remain open — this PR only adds pre-request throttling, not retry ([#60](https://github.com/exileum/meta-mcp/issues/60))
- **Automatic retry for transient Meta API failures** — `MetaClient.request()` now retries up to 3 times with exponential backoff (1s, 2s, 4s base, 0–25% jitter, capped at 60s) on HTTP `429`/`500`/`502`/`503`/`504` and on network errors thrown by `fetch` (`AbortError`/`TimeoutError`/`fetch failed`); a `Retry-After` response header in either seconds or HTTP-date form is honored when present (also capped at 60s). Permanent errors (every other `4xx`, including `400`/`401`/`403`/`404`) still fail fast on the first attempt — only transient categories are retried. Retry budget and base delay are tunable via two new optional `MetaClientOptions`: `maxRetries` (default `3`, set to `0` to disable, matches pre-fix behavior) and `retryBaseDelayMs` (default `1000`); test-only `sleep` and `now` hooks are also exposed for deterministic backoff tests without real waiting. After retries are exhausted the original `MetaApiError` / network error is rethrown unchanged, so `categorize()` in `src/utils/errors.ts` continues to route exhaustion failures to the existing `error_type: "rate_limit" | "server" | "network"` paths with their `remediation` hints — clients see the same JSON error shape introduced in [#114](https://github.com/exileum/meta-mcp/issues/114), just less often. Trade-off documented: writes (POST/DELETE) are retried too per the issue's explicit recommendation — Meta's endpoints either reject duplicate publishes idempotently (e.g., `"container already published"`) or produce a wasted-quota duplicate container, never silent data corruption. Worst-case end-to-end latency rises from ~30s (one timeout) to ~127s (four 30s timeouts plus 1+2+4s backoff); MCP hosts with short per-tool deadlines can construct `MetaClient` with `maxRetries: 0` to opt out. Pairs with the rate-limit and server remediation strings already present in [#114](https://github.com/exileum/meta-mcp/issues/114) ([#61](https://github.com/exileum/meta-mcp/issues/61))

### Fixed
- **`ig_publish_carousel` and `threads_publish_carousel` now create child containers in parallel** — child containers are independent per the [Instagram content publishing](https://developers.facebook.com/docs/instagram-platform/content-publishing/) and [Threads carousel posts](https://developers.facebook.com/docs/threads/posts) docs (creating one does not depend on another), but the previous `for…of` loop POSTed and polled them sequentially via `await waitForIgContainer()` / `waitForThreadsContainer()` before moving to the next item — so each child blocked the loop for up to its own poll-window (30s images / 300s videos). Concurrent POSTs sit well within Meta's documented content-publishing rate limits (no semaphore or chunking needed). ### Fixed
- **BREAKING: `ig_respond_collaboration_invite` used wrong parameter names and types** — replaced `invite_id` (string) + `action` (`"accept"`/`"decline"` enum) with `media_id` (string) + `accept` (boolean), matching the [Instagram Collaboration API](https://developers.facebook.com/docs/instagram-platform/instagram-api-with-facebook-login/collaboration) referenced in the [Dec 3 2025 Instagram Platform changelog](https://developers.facebook.com/docs/instagram-platform/changelog) ("Accept/Decline a collaboration invite using `media_id` of the tagged IG Media", `accept=true|false`). The endpoint URL `POST /{ig-user-id}/collaboration_invites` was already correct; only the body parameters were wrong, so the previous tool surface (introduced in v2.0.0) was silently rejected by Meta with a `(#100)` "param ... is not a valid field" error and the response action never took effect. Callers must now pass `media_id` (use the `id` field from the `ig_get_collaboration_invites` response) and `accept: true`/`false`; the Zod schema rejects the old shape so callers see a clear validation error instead of the silent Meta rejection ([#83](https://github.com/exileum/meta-mcp/issues/83))
- **`MetaClient` form-encoded params silently corrupted arrays/objects via `String(v)`** — the form-encoded path in `MetaClient.request()` coerced every value with `String(v)`, which produces `"1,2,3"` for arrays (no brackets, accidental CSV) and `"[object Object]"` for plain objects. All current call sites pass primitives (handlers stringify ahead of time via `JSON.stringify(...)` for `poll_attachment`, `gif_attachment`, `text_attachment`, `collaborators`, and `.join(",")` for `children` and `allowlisted_country_codes`), but the loose `Record<string, unknown>` boundary made the next non-primitive assignment a silent footgun. Now `MetaClient.ig()` / `threads()` / `meta()` declare `params?: FormParams` (where `FormParamValue = string | number | boolean | undefined | null`) so TypeScript flags non-primitive assignments at compile time, and the runtime `appendFormParams()` throws a clear error (`form parameter "<name>" has unsupported type "<typeof>"`) for any value that escapes the type system — covering objects, arrays, `bigint`, `Symbol`, and functions in one allowlist guard. The `RequestOptions.json: boolean` flag was replaced with `RequestOptions.jsonBody: Record<string, unknown>`: the only consumer (`ig_send_message`) now passes its nested `recipient`/`message` payload via `jsonBody` instead of conflating it with form params. Aligned with the milestone's type-safety overhaul; same pattern as [#24](https://github.com/exileum/meta-mcp/issues/24)'s `ClientResponse.data` tightening ([#81](https://github.com/exileum/meta-mcp/issues/81))
- **Resource handlers now sanitize errors and emit standard JSON-RPC error responses** — `instagram-profile` and `threads-profile` resource handlers (`src/resources/instagram.ts`, `src/resources/threads.ts`) previously had no `try`/`catch` around the `client.ig(...)` / `client.threads(...)` call, so any thrown error (missing token, missing user ID, network failure, `MetaApiError`) bubbled up to the MCP SDK's protocol layer and was forwarded as a generic JSON-RPC `InternalError` (`-32603`) with the **raw `error.message`** — bypassing the `sanitizeRaw()` redaction used by every tool handler and risking `access_token=…` leakage from request URLs in network-failure messages. Both handlers now wrap their work in `try`/`catch` and `throw toMcpResourceError(error, label)`, a new helper in `src/utils/errors.ts` that reuses the existing `categorize()` and `sanitizeRaw()` to build a sanitized `McpError` with structured `data` (`error_type`, `http_status`, `code`, `subcode`, `type`, `fbtrace_id`, `remediation`). Per the [MCP spec for resources](https://modelcontextprotocol.io/specification/2025-06-18/server/resources) ("Servers SHOULD return standard JSON-RPC errors for common failure cases") and consistent with how every tool handler reports failure. The JSON-RPC error code seen by clients is unchanged (`-32603`); the message is now sanitized and the response carries an `error.data` payload for client introspection. Connection stability is also unchanged — the SDK already caught unhandled throws (so the issue's "potentially crashing the server connection" framing was incorrect), but raw `error.message` could leak tokens, which this fix prevents ([#38](https://github.com/exileum/meta-mcp/issues/38))
- **`threads_publish_text` `alt_text` is now actually rejected at the schema level** — the v5.0.0 entry for [#185](https://github.com/exileum/meta-mcp/issues/185) claimed callers passing `alt_text` to `threads_publish_text` would now get a Zod schema error, but in practice the field was just omitted from the registered raw shape and `z.object()` defaults to `.strip()` — so the parameter was silently dropped and the post was published without it (live verification confirmed the post was created successfully when `alt_text` was passed). Restored the field as `z.never("…").optional()` so undefined still passes through but any defined value triggers a descriptive Zod issue pointing the caller at `threads_publish_image` / `threads_publish_video` / `threads_publish_carousel` instead. The handler-level mutual-exclusion checks added in [#185](https://github.com/exileum/meta-mcp/issues/185) are unchanged
- **`threads_reply` silently accepted both `image_url` and `video_url` on the same reply** — the handler would assign `mediaType = "VIDEO"` (overriding `"IMAGE"`) but still forward both URLs to `POST /{user-id}/threads`, sending Meta an undefined-behavior combination. Added a handler-level validation that fast-fails with a clear error when both are provided. Per the [Threads Posts docs](https://developers.facebook.com/docs/threads/posts), each `media_type` has exactly one required URL field (`image_url` for IMAGE, `video_url` for VIDEO) and the spec doesn't define behavior when both are sent. The tool description and the `image_url` / `video_url` `.describe()` strings now spell out the mutual-exclusion constraint. Same conservative pattern as the [#185](https://github.com/exileum/meta-mcp/issues/185) `threads_publish_text` attachment mutual-exclusion fix ([#59](https://github.com/exileum/meta-mcp/issues/59))
- **`threads_reply` with `video_url` timed out after 30s instead of polling for the full video processing window** — when a reply included a `video_url`, the call to `waitForThreadsContainer()` omitted its `maxWait` argument, falling back to the helper's image-tier default (30s). The publish-side tools (`threads_publish_video`, the carousel video children, etc.) had been bumped to a longer video timeout in [#118](https://github.com/exileum/meta-mcp/issues/118) (v4.0.0), but the same fix was never applied to `threads_reply`'s video branch — so any video reply that took longer than 30s to transcode failed with `Threads container processing timed out after 30s`. The reply branch now passes the explicit video timeout, matching the other video publish paths ([#49](https://github.com/exileum/meta-mcp/issues/49))
- **`threads_reply` with `image_url` skipped container status polling before publishing** — companion fix to the same gap [#29](https://github.com/exileum/meta-mcp/issues/29) closed for `threads_publish_image`: the `threads_reply` handler only polled `waitForThreadsContainer()` when `video_url` was set, so image replies could race ahead and call `threads_publish` while the container was still `IN_PROGRESS`, returning a "Cannot find media with the given ID" error for larger uploads. Image replies now poll for `FINISHED` with the 30s image-tier timeout before publishing, matching `threads_publish_image` ([#49](https://github.com/exileum/meta-mcp/issues/49))
- **Video container polling timeout raised from 120s to 300s and centralized as a named constant** — `src/utils/container.ts` now exports `IMAGE_PROCESSING_TIMEOUT` (30s) and `VIDEO_PROCESSING_TIMEOUT` (300s), and every publishing call site (`ig_publish_video`, `ig_publish_reel`, `ig_publish_story`, `ig_publish_carousel` video children, `threads_publish_video`, `threads_publish_carousel` video children, `threads_reply` video) imports and passes them instead of magic literals. The 300s ceiling matches Meta's [Instagram content publishing](https://developers.facebook.com/docs/instagram-platform/content-publishing/) guidance ("query a container's status once per minute, for no more than 5 minutes") and gives large videos (1GB / 5 min, the API maximum) headroom to finish transcoding without spurious timeouts. Image-only and carousel-parent waits (`ig_publish_photo`, `ig_publish_carousel` parent, `threads_publish_image`, `threads_publish_carousel` parent) keep the 30s default — by the time a parent carousel container is polled, every child is already `FINISHED`, so the parent is only assembling references ([#49](https://github.com/exileum/meta-mcp/issues/49))

### Changed
- **BREAKING: structured error responses across all tool handlers** — every tool that returns `isError: true` now emits a JSON-encoded body in `content[0].text` instead of a plain string like `"Publish photo failed: ..."`. Shape: `{ error: true, error_type: "auth" | "validation" | "rate_limit" | "server" | "network" | "internal", http_status?, code?, subcode?, type?, message, remediation?, fbtrace_id?, raw }`. Categorization keys off Meta API HTTP status, error code, subcode, and `OAuthException` type per the [Graph API error reference](https://developers.facebook.com/docs/graph-api/guides/error-handling/) (e.g., `190`/`OAuthException`/`401` → `auth`; `4`/`17`/`32`/`80001-80008`/`429` → `rate_limit`; `100`/`200`/`803` → `validation`; `1`/`2`/`5xx` → `server`); unmatched `4xx` HTTP statuses (`403`, `404`, `422`, etc.) fall through to `validation` so AI clients don't see misleading "retry" remediation on client-side errors; network/timeout failures from `fetch` (`AbortError`, `TimeoutError`, `fetch failed`) → `network`; internally-thrown `Error` (e.g., container creation guards) and `MetaApiError` with no `httpStatus` and no recognized code → `internal`. `remediation` is populated only where actionable (`auth` → token refresh hint, `rate_limit` → backoff, `server`/`network` → retry); `validation` and `internal` omit it. `raw` is sanitized — `access_token=...`, `client_secret=...`, and `input_token=...` query params and JSON values are scrubbed to `***` to prevent token leakage. Pre-validation `isError: true` returns (e.g., `text_attachment + poll_options` mutual-exclusion checks in `threads_publish_text`) use the same JSON shape with `error_type: "validation"`. AI clients that previously parsed the `"<Action> failed: <message>"` prefix must now `JSON.parse` the `text` field; the original message is preserved verbatim inside `message`. New `MetaApiError` class in `src/utils/errors.ts` carries `httpStatus`, `apiCode`, `apiSubcode`, `apiType`, `fbtraceId`, `endpoint`, `method`, `body` and is thrown by `MetaClient.request()` for both HTTP-error and JSON-error response paths; the human-readable `.message` format is unchanged so existing substring matches (e.g., the `"nonexisting field"` detection in `threads_get_container_status`) keep working ([#114](https://github.com/exileum/meta-mcp/issues/114))

- **npm provenance** — packages are now published with OIDC trusted publishing for verifiable supply chain security

### Fixed
- **Instagram API base URL** — use `graph.instagram.com` for Instagram endpoints; tokens from Instagram Login flow (`IGAA...`) were rejected by `graph.facebook.com`
- **Meta platform endpoints** — separate `FB_BASE` (`graph.facebook.com`) for token exchange, debug, and webhook tools that only exist on the Facebook Graph API
- **POST request encoding** — switch from `application/json` to `application/x-www-form-urlencoded` for POST requests; optional parameters like `topic_tag` and `poll` were silently ignored by the Meta API with JSON encoding
- Deduplicate URLSearchParams building logic in `meta-client.ts`
