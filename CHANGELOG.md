## [Unreleased]

### Added
- **`MetaClient` now self-throttles on `x-app-usage` to stay under Meta's per-app quota** — `parseRateLimit()` had been surfacing the snake_case header (`call_count`, `total_cpu_time`, `total_time`) as the camelCase `_rateLimit` field on every tool response since [#20](https://github.com/exileum/meta-mcp/issues/20), but the client never consulted the data and a burst of MCP tool calls walked straight into Meta's 100%-threshold throttle (HTTP 429, up to one hour lockout per the [Meta rate-limiting docs](https://developers.facebook.com/docs/graph-api/overview/rate-limiting/)). The client now caches the most recent `x-app-usage` snapshot on the `MetaClient` instance and sleeps before the next `fetch()` once `max(callCount, totalCpuTime, totalTime)` crosses one of two thresholds: 80% → 1000 ms slowdown, 90% → 5000 ms backoff. The `max(...)` picks up whichever quota Meta is rate-limiting on at the moment (request count, wall-clock, or CPU — Meta throttles on whichever hits 100% first). The first request after startup is never throttled (no snapshot yet). Snapshots only update when the header is present, so OAuth token endpoints (`graph.instagram.com/access_token`, `graph.threads.net/refresh_access_token`, etc.) leave existing throttle state intact rather than clearing it; the snapshot is also refreshed on error responses so a 429 immediately tightens the next call. Snapshots older than `RATE_LIMIT_SNAPSHOT_TTL_MS` (1 hour, Meta's rolling window) are discarded so a long-idle client doesn't pay a spurious backoff on its first post-idle call. The 30 s abort timer (`AbortSignal.timeout(30_000)`) is now armed **after** the throttle sleep so a 5 s backoff at high `x-app-usage` no longer eats into the network budget. As a side effect, `pollContainerStatus()` (used by every IG/Threads publish that creates a media container) now self-throttles too — a video publish near 90% usage may exhaust its 300 s timeout faster, which is the correct behavior: we *want* polling to slow down when we're near the cap. `parseRateLimit()` also gained defensive numeric coercion (`Number(v)`) so a future Meta API tweak (numbers shipped as strings) keeps producing usable values instead of silently leaving fields `undefined`. Each throttled call logs a single `[meta-mcp] x-app-usage at N%…` line to stderr (safe for stdio MCP). Thresholds and delays are exported as named constants (`RATE_LIMIT_SLOWDOWN_THRESHOLD`, `RATE_LIMIT_BACKOFF_THRESHOLD`, `RATE_LIMIT_SLOWDOWN_MS`, `RATE_LIMIT_BACKOFF_MS`, `RATE_LIMIT_SNAPSHOT_TTL_MS`) so the regression tests reference them by name. Issue [#61](https://github.com/exileum/meta-mcp/issues/61) (retry/backoff on 429) and [#72](https://github.com/exileum/meta-mcp/issues/72) (network error normalization) remain open — this PR only adds pre-request throttling, not retry ([#60](https://github.com/exileum/meta-mcp/issues/60))
- **Automatic retry for transient Meta API failures** — `MetaClient.request()` now retries up to 3 times with exponential backoff (1s, 2s, 4s base, 0–25% jitter, capped at 60s) on HTTP `429`/`500`/`502`/`503`/`504` and on network errors thrown by `fetch` (`AbortError`/`TimeoutError`/`fetch failed`); a `Retry-After` response header in either seconds or HTTP-date form is honored when present (also capped at 60s). Permanent errors (every other `4xx`, including `400`/`401`/`403`/`404`) still fail fast on the first attempt — only transient categories are retried. Retry budget and base delay are tunable via two new optional `MetaClientOptions`: `maxRetries` (default `3`, set to `0` to disable, matches pre-fix behavior) and `retryBaseDelayMs` (default `1000`); test-only `sleep` and `now` hooks are also exposed for deterministic backoff tests without real waiting. After retries are exhausted the original `MetaApiError` / network error is rethrown unchanged, so `categorize()` in `src/utils/errors.ts` continues to route exhaustion failures to the existing `error_type: "rate_limit" | "server" | "network"` paths with their `remediation` hints — clients see the same JSON error shape introduced in [#114](https://github.com/exileum/meta-mcp/issues/114), just less often. Trade-off documented: writes (POST/DELETE) are retried too per the issue's explicit recommendation — Meta's endpoints either reject duplicate publishes idempotently (e.g., `"container already published"`) or produce a wasted-quota duplicate container, never silent data corruption. Worst-case end-to-end latency rises from ~30s (one timeout) to ~127s (four 30s timeouts plus 1+2+4s backoff); MCP hosts with short per-tool deadlines can construct `MetaClient` with `maxRetries: 0` to opt out. Pairs with the rate-limit and server remediation strings already present in [#114](https://github.com/exileum/meta-mcp/issues/114) ([#61](https://github.com/exileum/meta-mcp/issues/61))
- **`messaging_type` and `tag` parameters on `ig_send_message`** — the handler previously hardcoded `messaging_type: "RESPONSE"` in the JSON body, locking callers into the 24-hour reply window even though the tool description advertised a "7-day for human agent" mode that had no way to actually be invoked. Two new optional parameters now expose the full [Send API surface](https://developers.facebook.com/docs/messenger-platform/reference/send-api/): `messaging_type` (`RESPONSE` default, `UPDATE`, or `MESSAGE_TAG`) and `tag` (Zod-enum of `HUMAN_AGENT`, `CONFIRMED_EVENT_UPDATE`, `POST_PURCHASE_UPDATE`, `ACCOUNT_UPDATE`, `CUSTOMER_FEEDBACK`). The Zod parameter is named `tag` to mirror the actual Meta API field 1:1 (same philosophy as [#83](https://github.com/exileum/meta-mcp/issues/83)), and the JSON body sent to `POST /{ig-user-id}/messages` now carries `tag` only when `messaging_type === "MESSAGE_TAG"`. Bidirectional handler-level validation rejects mismatched combinations with an `error_type: "validation"` response — `messaging_type=MESSAGE_TAG` without `tag` fast-fails with a clear error, and a stray `tag` when `messaging_type !== "MESSAGE_TAG"` is rejected rather than silently dropped (same conservative pattern as the `gif_id`/`gif_provider` co-dependency from [#77](https://github.com/exileum/meta-mcp/issues/77) and the `threads_publish_text` mutual-exclusion checks from [#185](https://github.com/exileum/meta-mcp/issues/185)). Default-callers see no behavior change: omitting both new parameters sends the same `messaging_type: "RESPONSE"` body as before. Tool description rewritten to explain the per-`messaging_type` window: `RESPONSE`/`UPDATE` → 24 h, `MESSAGE_TAG`+`HUMAN_AGENT` → 7 days (human-sent only per Meta's [Human Agent feature docs](https://developers.facebook.com/docs/features-reference/human-agent), App Review required); other tag values are Messenger-oriented and may be silently rejected on Instagram ([#53](https://github.com/exileum/meta-mcp/issues/53))

### Changed
- **Consolidated tool/resource/prompt registration into a single `registerAll()` helper** — `src/index.ts` previously listed the same 17 registration calls (14 tool registrars, 2 resource registrars, 1 prompt registrar) twice: once for the production stdio server and once inside `createSandboxServer()` for the Smithery sandbox. Adding a new tool module required editing both blocks, and forgetting to update the sandbox copy caused silent divergence — the Smithery sandbox would omit the new tool until somebody noticed. Extracted the sequence into a new module `src/register-all.ts` exporting `registerAll(server, client)`; both `src/index.ts` and `createSandboxServer()` now delegate to it. Registration order is preserved exactly, so the registered tool/resource/prompt sequence is byte-identical to before. Added `src/register-all.test.ts`, a snapshot test that asserts every expected tool name, resource URI, and prompt name in registration order — a future tool module wired up to only one of the two paths is now impossible because there is only one path. No public-API or behavior change: `createSandboxServer()` keeps the same signature and return type ([#47](https://github.com/exileum/meta-mcp/issues/47))

### Fixed
- **`ig_publish_carousel` and `threads_publish_carousel` now create child containers in parallel** — child containers are independent per the [Instagram content publishing](https://developers.facebook.com/docs/instagram-platform/content-publishing/) and [Threads carousel posts](https://developers.facebook.com/docs/threads/posts) docs (creating one does not depend on another), but the previous `for…of` loop POSTed and polled them sequentially via `await waitForIgContainer()` / `waitForThreadsContainer()` before moving to the next item — so each child blocked the loop for up to its own poll-window (30s images / 300s videos). For a 10-item video carousel that meant ~5 min worst-case latency instead of ~30s. Both handlers now use `Promise.all(items.map(async (item) => { … return childId; }))`, kicking off all child POSTs concurrently and polling them in parallel. A 10-item IG video carousel drops from ~300s worst-case to ~30s; a 20-item Threads carousel from ~600s to ~30s. Concurrent POSTs sit well within Meta's documented content-publishing rate limits (no semaphore or chunking needed). On any child failure `Promise.all` rejects with the first error (fast-fail UX — the caller doesn't wait for the remaining children's poll windows to elapse) and the parent carousel POST never runs; the original `MetaApiError` propagates unwrapped so `formatErrorResponse` keeps the correct categorization (`auth` / `rate_limit` / `validation` / `server` / `network`) and the Meta-supplied message naming the offending URL. Promise.all's combinator internally subscribes to every input promise, so the trailing children that reject after the first failure are consumed cleanly — no unhandled rejection warnings under Node's strict mode ([#48](https://github.com/exileum/meta-mcp/issues/48))

### Changed
- **BREAKING (for malformed configs only): `loadConfig()` now validates env-var credentials at startup via Zod** — `META_APP_ID` must be a numeric string (regex `/^\d*$/`); `INSTAGRAM_USER_ID` and `THREADS_USER_ID` must be a numeric string or the literal `"me"` (regex `/^(me|\d*)$/`) since [Meta's Threads API](https://developers.facebook.com/docs/threads/threads-profiles/) and the Graph API in general accept `"me"` as the authenticated-user alias on `/{user-id}/...` paths. Malformed values now fail fast at startup with `Invalid meta-mcp configuration: …` and exit code 1, instead of silently propagating to the Meta API and surfacing as a confusing `(#100) Tried accessing nonexisting field` later. Anyone whose env vars were already correct (numeric or `"me"`) sees no change. Also switched the per-field default fallback from `process.env.X || ""` to a Zod `.default("")` (semantic equivalent of `??`) so a literal `"0"` is no longer collapsed to `""` if Meta ever issues such an ID. `MetaConfig` is now `z.infer<typeof MetaConfigSchema>` — the runtime shape is identical (all `string`), so existing call sites compile unchanged. The `createSandboxServer()` Smithery sandbox builds `MetaConfig` inline so the sandbox path itself doesn't go through the schema; note however that importing `dist/index.js` still triggers the top-level `loadConfig()` (and `main()`) as a module side effect — this is pre-existing behavior, not introduced by this PR ([#26](https://github.com/exileum/meta-mcp/issues/26))
- **Startup warnings for partial / missing credentials** — `loadConfig()` now emits stderr warnings (via `console.error`, safe for stdio MCP since the protocol uses stdout) when (a) zero credentials are configured, (b) `INSTAGRAM_ACCESS_TOKEN` is set but `INSTAGRAM_USER_ID` is missing or vice versa, (c) the same for `THREADS_ACCESS_TOKEN` / `THREADS_USER_ID`, or (d) `META_APP_ID` / `META_APP_SECRET` are out of pair. Previously the server started silently and only failed at first tool invocation with messages like `"INSTAGRAM_ACCESS_TOKEN is not configured."` thrown lazily from `MetaClient.ig()` / `threads()` / `meta()` and the `igUserId` / `threadsUserId` getters; the runtime throw sites are unchanged so callers still get the same lazy errors as a backstop ([#26](https://github.com/exileum/meta-mcp/issues/26))
- **Meta Graph API and Threads API versions are now configurable via env vars** — `src/services/meta-client.ts` previously hardcoded the version segment in three URL string literals (`https://graph.instagram.com/v25.0`, `https://graph.facebook.com/v25.0`, `https://graph.threads.net/v1.0`). Meta cuts a new Graph API minor version every ~4 months and supports each for ~2 years per the [Graph API changelog](https://developers.facebook.com/docs/graph-api/changelog), so deprecation forced a meta-mcp release just to flip the string. Two new optional env vars — `META_API_VERSION` (defaults to `v25.0`, used by Instagram and Facebook endpoints) and `THREADS_API_VERSION` (defaults to `v1.0`, kept on a separate single-major-version track since launch) — let an operator override the resolved version at startup. Values must match `^v\d+\.\d+$`; malformed input falls back to the default with a `console.error` stderr warning rather than crashing the process (same warn-don't-crash tone as `warnIfMisconfigured()`'s partial-credential warnings; a wrong version string would surface as a Meta API 404 anyway). OAuth token endpoints (`graph.instagram.com/access_token`, `graph.threads.net/refresh_access_token`, etc.) remain deliberately unversioned per Meta's OAuth surface — `IG_TOKEN_BASE` / `THREADS_TOKEN_BASE` ignore both env vars, and the existing token-endpoint regression guard in `meta-client.test.ts` continues to pass. `MetaClient`'s constructor also accepts an optional `MetaClientOptions` second argument (`{ metaApiVersion?, threadsApiVersion? }`) so tests can override per-instance without `vi.stubEnv` choreography; production callers (`src/index.ts:49` and the Smithery sandbox at `src/index.ts:100`) keep using the single-arg form and see no behavior change. The `MetaConfigSchema` was deliberately left untouched — version is a runtime knob, not a credential, and conflating the two would muddy the schema introduced in [#26](https://github.com/exileum/meta-mcp/issues/26) ([#70](https://github.com/exileum/meta-mcp/issues/70))
- **Documented `zod` and other transitive runtime dependencies as internal** — added an "API Stability" section to `README.md` clarifying that meta-mcp is consumed as an MCP server runtime (via `npx @exileum/meta-mcp` or `node dist/index.js`); the only programmatic export is `createSandboxServer(): McpServer` from the package root, used by the Smithery sandbox. Confirmed via a `dist/index.d.ts` audit that no `zod` types flow through the public API surface, so `zod`'s 3 → 4 bump in [3.2.0](#320--2026-04-04) and the ongoing 4.x cadence (`^4.4.3` as of 5.0.0) are not semver-breaking for meta-mcp consumers. `@modelcontextprotocol/sdk` is called out as the one exception — `McpServer` is the return type of `createSandboxServer`, so a breaking change to it would also break the programmatic API; in practice the SDK follows semver and acts as an implicit peer dependency. Deep imports into the published `dist/` tree (e.g. `@exileum/meta-mcp/dist/schemas.js`) are blocked by the `package.json` `exports` map for any spec-compliant resolver and are explicitly not part of the public API ([#69](https://github.com/exileum/meta-mcp/issues/69))
- **`reply_control` `.describe()` now lists all five values and links the authoritative docs** — the four Threads publish tools (`threads_publish_text`, `threads_publish_image`, `threads_publish_video`, `threads_publish_carousel`) shared an identical inline `z.enum([...]).optional().describe("Who can reply")`; consolidated into a shared `replyControlSchema` whose `.describe()` enumerates the per-option behavior (`everyone` / `accounts_you_follow` / `mentioned_only` / `parent_post_author_only` / `followers_only`) and links the [Threads Reply Management docs](https://developers.facebook.com/docs/threads/reply-management/) which explicitly list all five values as accepted for `POST /{threads-user-id}/threads`. No enum change — same five values, same parameter name, same handler behavior; only the JSON-Schema description and source layout change. Resolves a doubt raised in [#76](https://github.com/exileum/meta-mcp/issues/76) where the original premise — that `parent_post_author_only` and `followers_only` were undocumented — was contradicted by the current Meta docs ([#76](https://github.com/exileum/meta-mcp/issues/76))
- **Documented when to use `RequestOptions.jsonBody` and audited every POST call site** — the JSDoc on `jsonBody` in `src/services/meta-client.ts` previously read "When set, sent as the application/json request body (e.g., Instagram Messaging API)", which gave future contributors no decision rule for new endpoints. Sharpened the comment to spell out the criterion: opt into JSON mode **only** when Meta's docs explicitly require `Content-Type: application/json`, default form-urlencoded for everything else, and stringify nested fields (`poll_attachment`, `gif_attachment`, `text_attachment`, `user_tags`) into a single form parameter — the runtime guard from [#81](https://github.com/exileum/meta-mcp/issues/81) (`appendFormParams` rejects raw objects/arrays at the form-encoding boundary) enforces this convention. Audited all 13 distinct POST endpoints: only `POST /{ig-user-id}/messages` (`ig_send_message`) uses `jsonBody` (delivered by [PR #134](https://github.com/exileum/meta-mcp/pull/134)), per the [Instagram Messaging Send API](https://developers.facebook.com/docs/instagram-platform/instagram-api-with-instagram-login/messaging-api) which mandates a JSON `recipient`/`message` envelope. The other 12 — `POST /app/subscriptions`, `POST /{threads-user-id}/threads`, `POST /{threads-user-id}/threads_publish`, `POST /{post-id}/repost`, `POST /{reply-id}/manage_reply`, `POST /{ig-user-id}/media`, `POST /{ig-user-id}/media_publish`, `POST /{ig-user-id}/collaboration_invites`, `POST /{media-id}/comments`, `POST /{comment-id}/replies`, `POST /{comment-id}`, `POST /{media-id}` — all send `application/x-www-form-urlencoded` with flat parameters and pre-stringified nested fields, matching the format Meta documents (the [App Subscriptions docs](https://developers.facebook.com/docs/graph-api/reference/v25.0/app/subscriptions) show `fields=about,picture` form-encoded with no nested-object parameters). No code-behavior change — JSDoc only ([#104](https://github.com/exileum/meta-mcp/issues/104))

### Fixed
- **BREAKING: `ig_respond_collaboration_invite` used wrong parameter names and types** — replaced `invite_id` (string) + `action` (`"accept"`/`"decline"` enum) with `media_id` (string) + `accept` (boolean), matching the [Instagram Collaboration API](https://developers.facebook.com/docs/instagram-platform/instagram-api-with-facebook-login/collaboration) referenced in the [Dec 3 2025 Instagram Platform changelog](https://developers.facebook.com/docs/instagram-platform/changelog) ("Accept/Decline a collaboration invite using `media_id` of the tagged IG Media", `accept=true|false`). The endpoint URL `POST /{ig-user-id}/collaboration_invites` was already correct; only the body parameters were wrong, so the previous tool surface (introduced in v2.0.0) was silently rejected by Meta with a `(#100)` "param ... is not a valid field" error and the response action never took effect. Callers must now pass `media_id` (use the `id` field from the `ig_get_collaboration_invites` response) and `accept: true`/`false`; the Zod schema rejects the old shape so callers see a clear validation error instead of the silent Meta rejection ([#83](https://github.com/exileum/meta-mcp/issues/83))
- **`MetaClient` form-encoded params silently corrupted arrays/objects via `String(v)`** — the form-encoded path in `MetaClient.request()` coerced every value with `String(v)`, which produces `"1,2,3"` for arrays (no brackets, accidental CSV) and `"[object Object]"` for plain objects. All current call sites pass primitives (handlers stringify ahead of time via `JSON.stringify(...)` for `poll_attachment`, `gif_attachment`, `text_attachment`, `collaborators`, and `.join(",")` for `children` and `allowlisted_country_codes`), but the loose `Record<string, unknown>` boundary made the next non-primitive assignment a silent footgun. Now `MetaClient.ig()` / `threads()` / `meta()` declare `params?: FormParams` (where `FormParamValue = string | number | boolean | undefined | null`) so TypeScript flags non-primitive assignments at compile time, and the runtime `appendFormParams()` throws a clear error (`form parameter "<name>" has unsupported type "<typeof>"`) for any value that escapes the type system — covering objects, arrays, `bigint`, `Symbol`, and functions in one allowlist guard. The `RequestOptions.json: boolean` flag was replaced with `RequestOptions.jsonBody: Record<string, unknown>`: the only consumer (`ig_send_message`) now passes its nested `recipient`/`message` payload via `jsonBody` instead of conflating it with form params. Aligned with the milestone's type-safety overhaul; same pattern as [#24](https://github.com/exileum/meta-mcp/issues/24)'s `ClientResponse.data` tightening ([#81](https://github.com/exileum/meta-mcp/issues/81))
- **Resource handlers now sanitize errors and emit standard JSON-RPC error responses** — `instagram-profile` and `threads-profile` resource handlers (`src/resources/instagram.ts`, `src/resources/threads.ts`) previously had no `try`/`catch` around the `client.ig(...)` / `client.threads(...)` call, so any thrown error (missing token, missing user ID, network failure, `MetaApiError`) bubbled up to the MCP SDK's protocol layer and was forwarded as a generic JSON-RPC `InternalError` (`-32603`) with the **raw `error.message`** — bypassing the `sanitizeRaw()` redaction used by every tool handler and risking `access_token=…` leakage from request URLs in network-failure messages. Both handlers now wrap their work in `try`/`catch` and `throw toMcpResourceError(error, label)`, a new helper in `src/utils/errors.ts` that reuses the existing `categorize()` and `sanitizeRaw()` to build a sanitized `McpError` with structured `data` (`error_type`, `http_status`, `code`, `subcode`, `type`, `fbtrace_id`, `remediation`). Per the [MCP spec for resources](https://modelcontextprotocol.io/specification/2025-06-18/server/resources) ("Servers SHOULD return standard JSON-RPC errors for common failure cases") and consistent with how every tool handler reports failure. The JSON-RPC error code seen by clients is unchanged (`-32603`); the message is now sanitized and the response carries an `error.data` payload for client introspection. Connection stability is also unchanged — the SDK already caught unhandled throws (so the issue's "potentially crashing the server connection" framing was incorrect), but raw `error.message` could leak tokens, which this fix prevents ([#38](https://github.com/exileum/meta-mcp/issues/38))
- **`threads_publish_text` `alt_text` is now actually rejected at the schema level** — the v5.0.0 entry for [#185](https://github.com/exileum/meta-mcp/issues/185) claimed callers passing `alt_text` to `threads_publish_text` would now get a Zod schema error, but in practice the field was just omitted from the registered raw shape and `z.object()` defaults to `.strip()` — so the parameter was silently dropped and the post was published without it (live verification confirmed the post was created successfully when `alt_text` was passed). Restored the field as `z.never("…").optional()` so undefined still passes through but any defined value triggers a descriptive Zod issue pointing the caller at `threads_publish_image` / `threads_publish_video` / `threads_publish_carousel` instead. The handler-level mutual-exclusion checks added in [#185](https://github.com/exileum/meta-mcp/issues/185) are unchanged
- **`threads_reply` silently accepted both `image_url` and `video_url` on the same reply** — the handler would assign `mediaType = "VIDEO"` (overriding `"IMAGE"`) but still forward both URLs to `POST /{user-id}/threads`, sending Meta an undefined-behavior combination. Added a handler-level validation that fast-fails with a clear error when both are provided. Per the [Threads Posts docs](https://developers.facebook.com/docs/threads/posts), each `media_type` has exactly one required URL field (`image_url` for IMAGE, `video_url` for VIDEO) and the spec doesn't define behavior when both are sent. The tool description and the `image_url` / `video_url` `.describe()` strings now spell out the mutual-exclusion constraint. Same conservative pattern as the [#185](https://github.com/exileum/meta-mcp/issues/185) `threads_publish_text` attachment mutual-exclusion fix ([#59](https://github.com/exileum/meta-mcp/issues/59))
- **`threads_reply` with `video_url` timed out after 30s instead of polling for the full video processing window** — when a reply included a `video_url`, the call to `waitForThreadsContainer()` omitted its `maxWait` argument, falling back to the helper's image-tier default (30s). The publish-side tools (`threads_publish_video`, the carousel video children, etc.) had been bumped to a longer video timeout in [#118](https://github.com/exileum/meta-mcp/issues/118) (v4.0.0), but the same fix was never applied to `threads_reply`'s video branch — so any video reply that took longer than 30s to transcode failed with `Threads container processing timed out after 30s`. The reply branch now passes the explicit video timeout, matching the other video publish paths ([#49](https://github.com/exileum/meta-mcp/issues/49))
- **`threads_reply` with `image_url` skipped container status polling before publishing** — companion fix to the same gap [#29](https://github.com/exileum/meta-mcp/issues/29) closed for `threads_publish_image`: the `threads_reply` handler only polled `waitForThreadsContainer()` when `video_url` was set, so image replies could race ahead and call `threads_publish` while the container was still `IN_PROGRESS`, returning a "Cannot find media with the given ID" error for larger uploads. Image replies now poll for `FINISHED` with the 30s image-tier timeout before publishing, matching `threads_publish_image` ([#49](https://github.com/exileum/meta-mcp/issues/49))
- **Video container polling timeout raised from 120s to 300s and centralized as a named constant** — `src/utils/container.ts` now exports `IMAGE_PROCESSING_TIMEOUT` (30s) and `VIDEO_PROCESSING_TIMEOUT` (300s), and every publishing call site (`ig_publish_video`, `ig_publish_reel`, `ig_publish_story`, `ig_publish_carousel` video children, `threads_publish_video`, `threads_publish_carousel` video children, `threads_reply` video) imports and passes them instead of magic literals. The 300s ceiling matches Meta's [Instagram content publishing](https://developers.facebook.com/docs/instagram-platform/content-publishing/) guidance ("query a container's status once per minute, for no more than 5 minutes") and gives large videos (1GB / 5 min, the API maximum) headroom to finish transcoding without spurious timeouts. Image-only and carousel-parent waits (`ig_publish_photo`, `ig_publish_carousel` parent, `threads_publish_image`, `threads_publish_carousel` parent) keep the 30s default — by the time a parent carousel container is polled, every child is already `FINISHED`, so the parent is only assembling references ([#49](https://github.com/exileum/meta-mcp/issues/49))

### Security

- **BREAKING: structured error responses across all tool handlers** — every tool that returns `isError: true` now emits a JSON-encoded body in `content[0].text` instead of a plain string like `"Publish photo failed: ..."`. Shape: `{ error: true, error_type: "auth" | "validation" | "rate_limit" | "server" | "network" | "internal", http_status?, code?, subcode?, type?, message, remediation?, fbtrace_id?, raw }`. Categorization keys off Meta API HTTP status, error code, subcode, and `OAuthException` type per the [Graph API error reference](https://developers.facebook.com/docs/graph-api/guides/error-handling/) (e.g., `190`/`OAuthException`/`401` → `auth`; `4`/`17`/`32`/`80001-80008`/`429` → `rate_limit`; `100`/`200`/`803` → `validation`; `1`/`2`/`5xx` → `server`); unmatched `4xx` HTTP statuses (`403`, `404`, `422`, etc.) fall through to `validation` so AI clients don't see misleading "retry" remediation on client-side errors; network/timeout failures from `fetch` (`AbortError`, `TimeoutError`, `fetch failed`) → `network`; internally-thrown `Error` (e.g., container creation guards) and `MetaApiError` with no `httpStatus` and no recognized code → `internal`. `remediation` is populated only where actionable (`auth` → token refresh hint, `rate_limit` → backoff, `server`/`network` → retry); `validation` and `internal` omit it. `raw` is sanitized — `access_token=...`, `client_secret=...`, and `input_token=...` query params and JSON values are scrubbed to `***` to prevent token leakage. - **`threads_get_post_insights` missing `shares` metric in defaults** — added `shares` to the default metric list for `threads_get_post_insights` (now `views,likes,replies,reposts,quotes,shares`); per the [Threads Insights API docs](https://developers.facebook.com/docs/threads/insights/), `shares` is a valid post-level metric distinct from `reposts` (reposts = the repost action; shares = sharing the post to Instagram Stories, DMs, or external links). Sibling fix to #140 which previously corrected the same defaults string by removing the invalid `clicks` metric ([#115](https://github.com/exileum/meta-mcp/issues/115))

## [3.9.0] — 2026-04-09

### Changed
- **`threads_publish_text` and `threads_reply` now publish text posts in a single API call by default** — both tools now pass `auto_publish_text=true` on the container-creation endpoint so the post is created **and** published in one HTTP request, instead of the previous two-step `POST /threads` → `POST /threads_publish` flow. This eliminates the `4279009` "container not propagated yet" race condition at its source (no second request → no propagation window) and saves one API round-trip per text post. For `threads_reply`, the optimization only applies when the reply is text-only — replies with `image_url` or `video_url` continue to use the two-step flow with container polling for video.
